大语言模型擅长组织语言，却不会天然掌握企业私有数据，也无法保证参数知识始终及时。RAG 的原始思路是把生成模型与可检索的外部记忆结合：回答前先找证据。今天的工程系统又在索引、召回、校验和流程控制上继续扩展了它。

先记住一件事

Hybrid、GraphRAG、RAPTOR、Self-RAG、CRAG、Adaptive、Agentic 和多模态 RAG 不是互斥的产品型号。它们解决检索链路上不同位置的问题，可以按实际失败案例组合使用。

01 / THE CASE

先看一个问题：iOS 用户为什么流失？

设想一家产品团队问内部助手：“最近一个月 iOS 用户流失率为什么上升？请给出最可能的原因和证据。”这只是一个示意案例，下文的版本号、工单和结论均为虚构，用来展示系统应如何工作。

USER QUESTION
“最近一个月 iOS 用户流失率为什么上升？是新版本、登录故障，还是活动结束造成的？”

答案可能分散在指标表、发布记录、客服工单、缺陷系统和一张漏斗截图中。单次 Top-K 文本检索即便找到了“用户流失”的相关段落，也未必找到异常开始时间、影响人群或因果链。系统需要先定位异常，再沿时间线查证，最后区分观察事实、合理推断和待验证假设。

02 / BASELINE

传统 RAG：一条链，两个阶段

离线阶段把文档解析、清洗、分块，补充标题、时间和权限，再建立向量或关键词索引。在线阶段对问题改写、召回候选、重排、组装上下文，最后让模型生成带引用的回答。

这条路径适合“报销截止日是哪天”一类局部事实题。故障却不一定出在 LLM：表格解析丢掉行列关系；Chunk 把标题与正文切开；向量召回漏掉 ERR_CONN_RESET、版本号或人名；Top-K 覆盖不到跨文档证据；过期和冲突内容没有过滤。升级之前应先定位失败发生在解析、召回、排序、上下文，还是生成。

03 / THE MAP

八种路线，分别改哪一层？

路线改变的位置在案例里能做什么主要代价
Hybrid / Advanced召回与排序关键词找版本号，语义搜索找相近投诉链路与调参
RAPTOR分层索引跨章节阅读一份很长的事故复盘建索引与摘要误差
GraphRAG实体、关系和社区连接版本、故障、团队和项目依赖抽取成本与图质量
Self-RAG模型的检索与反思学习何时检索、证据是否支撑说法专门训练或适配
CRAG检索质量纠错召回无关后改写查询或回退额外评估与检索
Adaptive RAG问题路由简单事实走短路，复杂归因走多轮误路由风险
Agentic RAG任务规划与工具调用依次查指标、发布、工单和缺陷延迟、预算与权限
Multimodal RAG非文本证据读取漏斗图、表格和页面布局索引与推理开销

这些能力通常叠加使用。对大多数知识库，先修好解析、Hybrid Search、Rerank、引用和拒答，比一次性加入全部路线更容易验证收益。

04 / WALKTHROUGH

让一次调查真正有据可依

假设系统先查询指标库，发现流失率在 9 月 12 日开始上升，且主要集中在 iOS 18 的新版本用户。这个结果只定位了何时、哪些人，不能直接证明原因。接下来才轮到检索系统分工。

1

Hybrid：先把候选证据找全

并行执行 BM25 关键词召回与 Embedding 语义召回：前者查 v4.8.2、AUTH-271 等精确标识，后者查“登录后被退出”“会话失效”等近义描述。用 RRF 融合，再经 Reranker 精排；同时按时间、租户和权限过滤，并扩展相邻段落。Azure AI Search 文档给出了全文检索、向量检索和 RRF 融合的工程示例。

2

CRAG：证据不合格，就纠正

假设首次召回主要是两年前的 Android 登录故障。检索评估器应把它判为低相关，触发查询改写、补充检索或拒答，而不是让模型硬写结论。CRAG 原论文引入轻量级评估器、纠正动作和文档分解重组；其中 Web Search 是论文中的扩展来源，企业系统仍应遵守数据权限与来源策略。

3

GraphRAG 与 RAPTOR：处理不同跨度

回答“哪些团队和依赖造成修复延后”，GraphRAG 可把版本、登录服务、投诉、修复任务和负责人连成关系：Local Search 查实体邻居，Global Search 归纳大量记录的共同主题，DRIFT 用社区信息拓宽局部搜索。若关键证据是一份很长的事故复盘，RAPTOR 的递归聚类与摘要树可先定位章节，再回到底层原文。前者偏关系，后者偏语义层级；摘要都不能替代原始证据。参见 GraphRAG 查询文档与 RAPTOR 论文。

4

Multimodal：别丢掉图表里的事实

如果异常只出现在漏斗截图或 PDF 表格中，纯 OCR 后切块可能打散图例、列标题和数值。可分别索引正文、表格和图片描述，或像 ColPali 那样对页面图像建立视觉检索表示；召回后仍需核对原始页面。

5

Adaptive 与 Agentic：决定走多远

Adaptive RAG 可把“v4.8.2 何时发布”路由到一次检索，把“流失原因是什么”路由到多步调查。Adaptive-RAG 论文用分类器在不检索、单步与迭代检索之间选择。Agentic RAG 则让一个 Agent 规划工具调用、根据中间证据追问并控制停止条件；它不要求必须有多个 Agent。参见 Agentic RAG 综述。

Self-RAG 不等于普通的“请模型检查答案”。原论文通过训练模型生成 Reflection Tokens，让模型学习按需检索、判断段落相关性与证据支持程度。工程上可以另做答案核验步骤，但应准确称为工作流校验。

微软曾在 AP News 数据集的 50 个全局问题上报告，GraphRAG 动态社区选择在限定相同搜索深度时，平均 Token 成本相对静态 Global Search 低约 77%，回答质量相近。更深层级的搜索成本也可能上升。这是特定实验条件下的结果，不是项目预算承诺。

05 / DECISION

选型顺序：先看失败，再加能力

编号、人名、错误码漏召回BM25 + 向量混合检索；检查分块和元数据
长报告跨章节理解困难RAPTOR / 分层索引，答案回溯原文
大量文档的主题与依赖关系GraphRAG，评估图质量与索引成本
召回质量波动大CRAG 或确定性的评估与回退分支
问题难度差异大Adaptive 路由，低置信度回退到检索
跨知识库、数据库、Web 与 APIAgentic 调度，限制权限、次数和预算
证据在表格、图片与版面里多模态解析或视觉检索

可落地的顺序是：可靠解析 → 混合召回 → 重排 → 引用与拒答 → 离线评测集 → 针对失败案例加入图、纠错、路由或 Agent。检索层看 Recall@K、MRR、nDCG 和关键证据是否入选；生成层核对正确性、忠实度与引用；系统层记录 P95 延迟、Token、索引成本和新鲜度；业务层追踪任务完成率、人工接管率与高风险错误。RAGAS可辅助自动评估，关键场景仍需人工审核的真实问题集。

上线时的边界

对 Agent 设置只读工具权限、最大迭代次数与预算，记录每一步查询、召回、工具调用及引用。外部网页和文档可能包含提示注入；医疗、金融、法律等高风险结论还需要来源核验与人工复核。

成熟的 RAG，是能用可评估、可追溯的证据链稳定回答目标问题的系统。
